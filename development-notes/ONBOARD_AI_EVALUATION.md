# Onboard AI Controller Evaluation

本文档用于阶段 10：将电脑端 AI 控制器迁移到板载 AI 主控制器前的评估。当前只做软件和架构准备，不采购、不连接、不烧录任何新硬件。

## 迁移前提

- 电脑端 AI 控制器基础工程已可通过 Mock 测试。
- 模拟系统可验证命令、状态、急停、通信超时、传感器安全层和视觉回放。
- ESP32 固件仍保留最终安全决策权。
- AI 主控制器只发送高级命令，不直接控制单个舵机角度。

## 候选硬件

### Raspberry Pi 系列

优势：

- 生态成熟，摄像头、音频、Python、OpenCV 和推理工具链资料多。
- GPIO、USB、I2C、SPI、UART 外设支持广。
- 适合先做原型和调试。

风险：

- 满载功耗和发热需要评估。
- 供电和电池续航压力较大。
- 部分模型需要额外加速器才能流畅运行。

适合阶段：

- 电脑端功能迁移原型。
- 摄像头、语音和轻量模型联调。

### Raspberry Pi Compute Module 5 / CM 系列

优势：

- 更适合最终集成到机器人结构中。
- 可通过载板定制电源、接口和安装方式。

风险：

- 需要载板设计或选型。
- 调试门槛高于普通开发板。
- 不应在软件功能稳定前过早投入 PCB 或结构改造。

适合阶段：

- 电脑端和普通开发板原型稳定后，再评估最终集成。

### 其他单板计算机

候选方向：

- 低功耗 Linux SBC。
- 带 NPU 的边缘 AI 开发板。
- 小型 x86 主板。

评估重点：

- Python 运行环境。
- OpenCV 支持。
- 本地语音和视觉模型支持。
- USB 摄像头和音频设备兼容性。
- 功耗、散热、尺寸、重量和电池续航。

## 外设需求

### 摄像头

最低需求：

- 支持电脑端已有 `CameraSource` 抽象。
- 能提供稳定帧率和可测延迟。
- 支持无摄像头时回退到测试图片或视频回放。

待验证：

- 实际分辨率和帧率。
- 暗光表现。
- 安装角度和视野。
- 数据线固定方式。

### 麦克风

最低需求：

- 支持本地唤醒词和语音识别模块接入。
- 默认不提交私人录音。
- 支持关闭录音和 Mock 输入。

待验证：

- 机器人舵机噪声下的识别效果。
- 麦克风阵列是否必要。
- 本地降噪和回声消除方案。

### 扬声器

最低需求：

- 支持本地 TTS 输出。
- 音量足够但不影响麦克风过多。

待验证：

- 供电噪声。
- 安装位置。
- 与机器人结构共振情况。

### 电源与电池

最低需求：

- AI 主控制器和 ESP32/舵机电源域清晰。
- 共地设计明确。
- 电池状态可被安全层读取。

待验证：

- 峰值电流。
- 欠压行为。
- 散热。
- 续航时间。
- 急停时各电源域行为。

## 软件迁移要求

- 保持 `mock`、`simulator`、`real_robot` 配置切换。
- 上层控制逻辑不得因目标硬件改变而重写。
- 真实硬件接入前必须先通过模拟场景测试。
- 摄像头、语音、检测、人脸识别、追踪、安全层和助手模块保持解耦。
- API Key、Wi-Fi 密码、人脸数据和录音不得提交。

## 硬件在环门槛

进入硬件在环前必须完成：

- Mock 机器人服务器通过。
- 场景测试运行器通过。
- 状态可视化可用。
- 视觉回放 Mock 和测试图片目录通过。
- 传感器安全层 Mock 测试通过。

硬件测试顺序：

1. 只连接板载 AI 主控制器，不连接 ESP32。
2. 连接 ESP32，但不连接舵机。
3. 测试网络状态查询和急停命令。
4. 测试单个舵机。
5. 架空测试 8 舵机。
6. 最后才允许地面运动测试。

## 当前结论

当前不建议采购或定型板载 AI 主控制器。下一步应继续：

- 完善模拟系统和视觉回放。
- 在电脑端完成真实摄像头和 OpenCV 环境验证。
- 明确模型计算量和实时性需求。
- 明确电源预算和结构空间。
