# Hardware Checkpoints

本文档列出必须由用户手动完成的真实硬件检查点。软件代理不会自动烧录、打开串口、驱动舵机或控制机器人运动。

## 软件模拟优先规则

真实硬件测试前，必须优先完成电脑模拟测试系统中的对应场景：

- Mock 机器人服务器验证协议兼容性。
- 场景测试运行器验证命令序列和状态断言。
- 简单可视化验证状态显示。
- 视觉回放测试验证视觉模块与控制模块解耦。

普通软件模拟和自动化测试可以由软件代理自动执行、提交和推送。任何涉及真实 ESP32、串口、舵机、真实摄像头或真实传感器的测试，都必须暂停并等待用户明确确认。

## 检查点 1：烧录前目视检查

需要用户执行：

- 确认 ESP32 开发板型号与固件目标一致。
- 确认舵机接线、OLED I2C 接线、电源正负极和共地连接。
- 确认电池电压、供电能力和开关状态。
- 确认腿部机构没有卡死，周围没有阻挡物。

风险：

- 接线错误可能损坏开发板、OLED、舵机或电池。
- 机械卡死时上电可能导致舵机过流或过热。

预期结果：

- 接线与项目文档一致。
- 舵机和连杆可在断电状态下安全检查。

失败后的恢复：

- 立即断电。
- 按接线图逐项复查。
- 不继续烧录或运动测试。

完成后需要回复的最少信息：

- 开发板型号。
- 供电方式。
- 是否发现接线或机械异常。

## 检查点 2：固件烧录

需要用户执行：

```powershell
powershell -ExecutionPolicy Bypass -File ".\scripts\firmware-build.ps1"
```

随后用户可在确认安全后使用 Arduino IDE 或用户手动命令烧录。软件代理不会执行 `arduino-cli upload`。

风险：

- 选错开发板或端口会导致烧录失败。
- 烧录后设备可能立即初始化外设。

预期结果：

- 编译成功。
- 烧录工具显示上传成功。
- 开发板重启后无异常发热、异味或反复复位。

失败后的恢复：

- 断开电源。
- 检查 USB 线、端口、开发板型号和 BOOT 模式。
- 不连接舵机电源时先验证开发板可正常启动。

完成后需要回复的最少信息：

- 是否烧录成功。
- 使用的开发板和端口。
- 启动后是否出现异常复位、发热或异味。

## 检查点 3：串口只读启动日志

需要用户执行：

- 在确认不会发送运动命令的前提下打开串口监视器。
- 波特率设置为 115200。
- 只观察启动日志，不输入动作命令。

风险：

- 串口误输入运动命令可能驱动舵机。
- 连接舵机电源时错误固件可能导致机械动作。

预期结果：

- 能看到启动信息、网络信息或控制提示。
- 没有反复重启或 brownout 信息。

失败后的恢复：

- 关闭串口监视器。
- 断开舵机电源。
- 保存最短错误信息给软件侧分析。

完成后需要回复的最少信息：

- 是否看到启动日志。
- 是否有 brownout、重启循环或异常报错。
- 设备显示的 IP 或 AP 信息。

## 检查点 4：软件急停静态验证

需要用户执行：

- 在机器人处于安全支撑、舵机不会带动腿部碰撞的条件下测试急停命令。
- 先发送 `emergency_stop` 或 `estop`。
- 再尝试普通动作命令，确认不会执行。
- 发送 `reset_emergency_stop` 后确认机器人保持无动作，只有新命令才会动作。

风险：

- 如果急停实现或上传版本不正确，机器人可能继续执行旧动作。
- 解除急停后误发动作命令可能导致运动。

预期结果：

- 急停后动作停止。
- 急停期间普通动作无效。
- 解除急停后不恢复旧动作。

失败后的恢复：

- 立即断开舵机电源。
- 记录发送的最短命令序列和观察到的行为。
- 不继续行走测试。

完成后需要回复的最少信息：

- 急停是否停止动作。
- 急停期间普通命令是否被阻断。
- 解除急停后是否保持无动作。

## 检查点 5：通信超时软停止验证

状态：等待阶段 1 实现后执行。

需要用户执行：

- 将机器人架空或放在不会跌落的位置。
- 启动连续运动命令。
- 停止发送心跳或关闭控制页面。
- 观察机器人是否自动停止连续运动。

风险：

- 超时逻辑错误可能导致连续运动不停止。
- 放在桌面边缘可能跌落。

预期结果：

- 通信超时后连续运动自动停止。
- 不触发锁存急停。
- 恢复通信后需要新命令才能继续运动。

失败后的恢复：

- 立即发送 `emergency_stop`。
- 如果无效，断开舵机电源。
- 记录网络路径、命令和停止延迟。

完成后需要回复的最少信息：

- 是否自动停止。
- 大约停止延迟。
- 是否误触发急停。

## 检查点 6：硬件在环测试分级流程

状态：等待用户明确确认。

必须按以下顺序执行，不得跳级：

1. 只连接 ESP32，不连接舵机。
2. 测试单个舵机。
3. 架空进行 8 舵机测试。
4. 最后才允许地面运动测试。

风险：

- 连接真实 ESP32 或舵机可能造成误动作、过流、机械干涉或跌落。
- 地面运动测试可能损坏舵机、电池、开发板或机械结构。

预期结果：

- 每一步都能通过与模拟场景一致的命令和状态检查。
- 任一步骤失败都立即停止，不自动进入下一步。

失败后的恢复：

- 立即发送 `emergency_stop`。
- 如果软件命令无效，断开舵机电源。
- 记录最短命令序列、观察到的状态和硬件异常。

完成后需要回复的最少信息：

- 当前执行到哪一级硬件在环测试。
- 是否出现异常动作、发热、brownout 或机械卡滞。
- 是否可以继续下一等级测试。
